# Introduce the native Unity campus client while retaining Java authority

Ticket #58 replaces the browser presentation with a Unity desktop Game for Windows and macOS. Java continues to own Membership, the Game clock, reachable movement and every per-recipient result; the native client predicts only its own Avatar. Arrival-stamped events are queued and applied at Unity frame boundaries, while heartbeat timing remains independent of rendering. Native restart intent recovers a reserved Membership rather than creating a persistent account identity.

The compressed Kalapet Main Campus has one canonical publication for Java and Unity. Its coordinate mapping affects presentation only: authoritative positions and movement remain on the existing ground plane. Versioned 3D Avatar publications retain one backend reader and immutable per-Room collections, with optional complete sprite representations while legacy consumers migrate. Unsupported representations fail explicitly.

This migration costs a second temporary client and contract representation. The browser, old Town Maps and sprite-only workflows remain until their meaningful coverage and consumers have migrated, then are removed under #86. The bootstrap and transitional assets are internal preparation, not evidence that the complete migration in #87 has passed. Blender and Unity automation are local development tools; they confer no Game authority and are excluded from release runtime control.
