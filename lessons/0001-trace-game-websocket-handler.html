Lesson 0001 · about 8 minutes

Trace one WebSocket through PU Town

Your win: explain where Spring stops and PU Town begins, then narrate a Player's connection, Join, movement, and departure.

Guiding model: Spring delivers lifecycle events; GameWebSocketHandler turns them into authoritative game transitions.

1. First split the responsibilities

Framework

Spring WebSocket

WebSocketConfig maps the handler to /ws/game. After a successful HTTP upgrade, Spring invokes connection, text-message, and close callbacks with a WebSocketSession.

Application

PU Town

The handler creates Player identity, decodes protocol v1, manages Room membership, validates positions, and decides which server events each Player receives.

This is the architectural hinge: a WebSocket connection is only a transport relationship. It becomes a PU Town Room Membership only after a valid join_room command.

2. Follow the lifecycle

  1. 1

    HTTP upgrades to WebSocket

    WebSocketConfig registers the singleton handler at /ws/game and restricts browser origins.

  2. 2

    Spring reports a connection

    afterConnectionEstablished issues a Player ID, creates PlayerState, and adds three lookup entries: session → Player, ID → Player, and ID → outbox.

  3. 3

    A text frame arrives

    handleTextMessage finds the Player, synchronizes on it, strictly decodes the JSON, then dispatches one sealed command: Join, Leave, or Move. Decode failures become an error event.

  4. 4

    Join creates Room Membership

    handleJoin locks every involved Room in deterministic order. It ends an old membership if needed, resets the Player to the Spawn Point, announces player_joined to existing Players, and sends the joining Player a complete Room Snapshot.

  5. 5

    Move crosses the authority boundary

    handleMove requires Room Membership, locks that Room, and asks RoomRules whether the absolute position is finite, in bounds, and plausible. Only then does it update state and broadcast player_moved.

  6. 6

    Delivery is queued, not written inline

    deliver serializes a ServerMessage and enqueues it in the recipient's ConnectionOutbox. The executor performs actual socket writes sequentially, outside the Room transition.

  7. 7

    Leave and Disconnect remain different

    Leave clears roomId, tells others the reason was left, and acknowledges with room_left. A later close sees no membership. An unexpected close ends membership with reason disconnected.

Why the outbox matters: Spring warns that standard WebSocket sessions do not allow concurrent sends. PU Town's queue gives each connection one drain loop, preserves structural-event order, replaces superseded unsent movement, caps the queue at 256, and closes a connection that cannot accept essential events.

3. See the concurrency architecture

Shared handler
ConcurrentHashMap protects its registries.
Per Player
synchronized prevents message/close races.
Per Room
ordered locks serialize transitions and event creation.
Per connection
one bounded outbox serializes network writes.

These scopes are deliberately narrower than one global lock: unrelated Rooms can progress independently, while Players in the same Room observe a consistent event order.
